# Agrijuune --- Database Design

**Database:** Supabase PostgreSQL\
**Scope:** First-release enquiry capture and invite-only team access\
**Status:** The owner authorized and the prototype schema was applied to
live Supabase on 2026-11-24. This is schema-only approval; collecting
enquiry data remains blocked by the privacy and deletion prerequisites
below. The team-membership migration was applied to both production and
the confirmed non-production `juune-phase2-test` project on 2026-11-24.
Hosted Auth is configured for invite-only access, but production team
sign-in is not ready until the Vercel Vite Supabase variables are set and
staging acceptance tests pass.

## 1. Database scope

The first release needs a small database footprint. Its planned
persistence requirement is public website enquiries. The approved
`team_members` table stores invite-only team access roles; it does not
store application profiles or customer data.

Do not create farm, machinery, maintenance, inventory, tenant or
detailing-operation tables for a future farm platform unless separately
approved. Do not treat `team_members` as a general user or tenant model.
The standard demo should use fictional sample data and does not need
production farm records.

## 2. Access architecture

``` text
Public browser
   |
   | POST /api/v1/enquiries
   v
Express API
   |
   | server-side Supabase client
   v
Supabase PostgreSQL
```

Team sign-in is a separate browser-to-Supabase Auth flow. The browser
uses only the public anon key; `team_members` RLS grants a signed-in
member access only to their own role, and admins can manage team-role
rows. This membership is not permission to read enquiries or other
private records. See [Team access](./TEAM_ACCESS.md).

The browser must not receive the Supabase service-role key. The
preferred design is for the browser to submit enquiries only to the
Express API, which validates and persists them.

The backend has a typed, server-only Supabase enquiry repository behind
a service interface. It returns the generated enquiry ID, replay flag
and safe notification status, or a safe unavailable result. When
explicitly enabled, the service persists `pending` before sending an
email and then stores the outcome. It does not notify again for an
idempotent replay. `ENQUIRY_EMAIL_NOTIFICATIONS_ENABLED` defaults to
`false`. The collection route is mounted only when both
`ENQUIRY_COLLECTION_ENABLED` and `ENQUIRY_PRIVACY_GATES_VERIFIED` are
true and Supabase is configured; these settings default to false.
Repository, service and route tests use mocked dependencies; no enquiry
records are created by the test suite.

## 4. Versioned migration

The source of truth is
[`20261124095323_create_enquiries.sql`](../supabase/migrations/20261124095323_create_enquiries.sql).
It enforces bounded text lengths, non-negative counts, the approved
service IDs and controlled status values. It adds only a creation-time
index; one person may submit more than one enquiry, so email is not
unique. The migration creates no sample records, triggers, or access
policies. It was applied through the authenticated Supabase Dashboard SQL
Editor after the CLI's configured database password failed
authentication. The same migration version, name and five SQL statements
were recorded in `supabase_migrations.schema_migrations`. No enquiry
records were inserted in production.

The same migration was applied to the user-confirmed non-production
`juune-phase2-test` project through the authenticated Dashboard SQL
Editor. Its migration history records version `20261124095323` with the
five source statements. This environment has no staging API and received
no enquiry records.

[`20261124203100_create_team_members.sql`](../supabase/migrations/20261124203100_create_team_members.sql)
was applied through the authenticated Dashboard SQL Editor to both
production and `juune-phase2-test` on 2026-11-24. The `team_members`
table, admin seed, role function, RLS enablement and three policies were
verified in both projects. The migration version and name are recorded
in each project's migration history. This adds no enquiry access or
enquiry records; hosted Auth configuration and frontend environment
variables remain separate rollout steps.

[`20261124141740_add_enquiry_idempotency.sql`](../supabase/migrations/20261124141740_add_enquiry_idempotency.sql)
adds a nullable key hash, a keyed request fingerprint, a paired-format
constraint and a partial unique index. It does not insert or update
enquiry data and has not been applied to any database. The key and
fingerprint are stored on the enquiry row so the existing retention
deletion removes them together; do not enable collection until the
documented deletion process is scheduled and verified.

## 5. Row Level Security

Enable RLS:

``` sql
alter table public.enquiries enable row level security;
```

For the initial architecture:

-   Do not create anonymous `SELECT`, `UPDATE` or `DELETE` policies.
-   Prefer no direct anonymous `INSERT` policy because submissions go
    through the backend.
-   The migration revokes table privileges from `PUBLIC`, `anon` and
    `authenticated`, and grants only the CRUD privileges needed by the
    server-only `service_role`.
-   Backend access must use a server-only privileged credential and must
    be carefully constrained.
-   If the project later adopts a non-service database role, grant only
    the exact insert/read permissions required and add narrowly scoped
    policies.
-   Test access as anonymous and authenticated roles; do not assume RLS
    is working merely because it is enabled.

The service-role key bypasses RLS. Its security therefore depends on
strict server-side handling, access controls and never exposing it to
the browser.

Run [`enquiries_rls.sql`](../supabase/tests/enquiries_rls.sql) against a
non-production database after applying the schema. It checks RLS,
policies, role privileges and the server role's RLS bypass using
catalogue metadata only; it does not read or write enquiry records.
The test passed against `juune-phase2-test` on 2026-11-24.

## 6. Data validation

Validate at the API boundary and enforce database constraints as defence
in depth.

-   Trim strings.
-   Enforce maximum lengths.
-   Validate email format.
-   Validate service identifiers against an approved allowlist.
-   Reject negative machine counts.
-   Limit free-text message length.
-   Do not trust client-provided timestamps, notification status or lead
    status.
-   Set server-controlled fields in backend code.

## 7. Migrations and schema change process

-   Keep schema changes in version-controlled migration files.
-   Never make undocumented production schema changes manually.
-   Review the impact on repository code, API contracts and tests.
-   Prefer testing migrations against a non-production database first.
    The user-confirmed `juune-phase2-test` project is designated for
    isolated schema and RLS verification; it is not a staging API and
    must not contain production personal data. The initial live migration
    was a specifically authorized schema-only exception. That exception
    does not authorize data writes or future production schema changes
    without review and approval.
-   The initial live migration was run through the Dashboard SQL Editor
    and its version was recorded in the Supabase migration-history
    table. Correct the local CLI database password before using the
    documented CLI workflow for later migrations.
-   Use forward migrations and a documented recovery approach.
-   Update this document when schema, constraints, indexes or RLS
    policies change.

Use the pinned CLI in the repository. Authenticate and link the intended
project, inspect the pending changes, and only then apply them:

```sh
npx supabase login
npx supabase link --project-ref <PROJECT_REF>
npx supabase db push --remote --dry-run
npx supabase db push --remote
```

CI runs `npm run check:migrations` without database credentials or Docker.
It checks migration filenames and version uniqueness, rejects empty
migrations, and blocks direct data writes to `public.enquiries`. This is
an offline safety check, not a PostgreSQL parser or substitute for
reviewing and applying a migration to the confirmed non-production
project first.

Do not pass credentials as command-line arguments or commit local CLI
state. The linked project reference is stored under the ignored
`supabase/.temp/` directory. When local Docker-based testing is
available, use `npx supabase start` and `npx supabase db reset`; never
link a local or preview environment to production data. The CLI targets
the local database by default; always include `--remote` when applying
migrations to the explicitly linked project.

If a migration fails or needs correction, use a reviewed forward
migration; do not drop the table or delete records as an automatic
rollback.

## 8. Retention, deletion and backups

The product owner set a seven-day retention period for enquiry database
records, starting at submission, and a maximum seven-day target for
stored backups. The Supabase dashboard was checked on 2026-11-25: both
production and staging use the Free Plan, which does not include project
backups. The backup-retention target is therefore not met; the earlier
owner-reported confirmation was contradicted by the dashboard. The backend provides
`npm run purge:expired-enquiries --workspace backend`, which deletes
records whose `created_at` is earlier than the seven-day cutoff and
reports only the deleted count. It also requires the explicit
`ENQUIRY_RETENTION_PURGE_ENABLED=true` opt-in. The command has mocked
tests, but no scheduled execution is configured and the retention
process has not been verified in a database. Keep collection disabled
until an appropriate daily schedule and verification process are
configured and adequate backup retention is available. This retention
decision alone does not authorize collection.

The idempotency migration is still unapplied to databases. Apply and
verify it through the reviewed migration process before enabling the
public API; do not treat successful application as authorization to
collect enquiry data.

Before launch, define and verify:

-   Who may access enquiry records.
-   The daily schedule and monitoring for
    `purge:expired-enquiries`, including verification that it succeeds.
-   How deletion requests are assessed and actioned.
-   Whether backups retain deleted records and how the seven-day
    maximum will be enforced once an eligible plan or alternative is
    selected.
-   How database backups and restoration are tested.
-   Whether exports are needed and how they are protected.

## 9. Future platform data

A future farm-management product could require tenant/farm, user,
membership, machinery, maintenance, inventory, detailing and audit
tables. None of those entities should be implemented as part of the
current public website without an approved scope, tenant-isolation
design and data-ownership decision.
