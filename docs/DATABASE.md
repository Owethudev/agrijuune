# Agrijuune --- Database Design

**Database:** Supabase PostgreSQL\
**Scope:** First-release public website enquiry capture\
**Status:** The owner authorized and the prototype schema was applied to
live Supabase on 2026-11-24. This is schema-only approval; collecting
enquiry data remains blocked by the privacy and deletion prerequisites
below.

## 1. Database scope

The first release needs a small database footprint. Its primary
persistence requirement is public website enquiries.

Do not create farm, machinery, maintenance, inventory, user, tenant or
detailing-operation tables for a future farm platform unless separately
approved. The standard demo should use fictional sample data and does
not need production farm records.

## 2. Access architecture

``` text
Public browser
   |
   | POST /api/v1/enquiries
   v
Express API
   |
   | server-side Supabase client
   v
Supabase PostgreSQL
```

The browser must not receive the Supabase service-role key. The
preferred design is for the browser to submit enquiries only to the
Express API, which validates and persists them.

## 4. Versioned migration

The source of truth is
[`20261124095323_create_enquiries.sql`](../supabase/migrations/20261124095323_create_enquiries.sql).
It enforces bounded text lengths, non-negative counts, the approved
service IDs and controlled status values. It adds only a creation-time
index; one person may submit more than one enquiry, so email is not
unique. The migration creates no sample records, triggers, or access
policies. It was applied through the authenticated Supabase Dashboard SQL
Editor after the CLI's configured database password failed
authentication. The same migration version, name and five SQL statements
were recorded in `supabase_migrations.schema_migrations`. No enquiry
records were inserted.

## 5. Row Level Security

Enable RLS:

``` sql
alter table public.enquiries enable row level security;
```

For the initial architecture:

-   Do not create anonymous `SELECT`, `UPDATE` or `DELETE` policies.
-   Prefer no direct anonymous `INSERT` policy because submissions go
    through the backend.
-   The migration revokes table privileges from `PUBLIC`, `anon` and
    `authenticated`, and grants only the CRUD privileges needed by the
    server-only `service_role`.
-   Backend access must use a server-only privileged credential and must
    be carefully constrained.
-   If the project later adopts a non-service database role, grant only
    the exact insert/read permissions required and add narrowly scoped
    policies.
-   Test access as anonymous and authenticated roles; do not assume RLS
    is working merely because it is enabled.

The service-role key bypasses RLS. Its security therefore depends on
strict server-side handling, access controls and never exposing it to
the browser.

## 6. Data validation

Validate at the API boundary and enforce database constraints as defence
in depth.

-   Trim strings.
-   Enforce maximum lengths.
-   Validate email format.
-   Validate service identifiers against an approved allowlist.
-   Reject negative machine counts.
-   Limit free-text message length.
-   Do not trust client-provided timestamps, notification status or lead
    status.
-   Set server-controlled fields in backend code.

## 7. Migrations and schema change process

-   Keep schema changes in version-controlled migration files.
-   Never make undocumented production schema changes manually.
-   Review the impact on repository code, API contracts and tests.
-   Prefer testing migrations against a non-production database first.
    No separate project is currently configured; the owner has
    specifically authorized this initial schema-only migration against
    the live project. That exception does not authorize data writes or
    future production schema changes without review and approval.
-   The initial live migration was run through the Dashboard SQL Editor
    and its version was recorded in the Supabase migration-history
    table. Correct the local CLI database password before using the
    documented CLI workflow for later migrations.
-   Use forward migrations and a documented recovery approach.
-   Update this document when schema, constraints, indexes or RLS
    policies change.

Use the pinned CLI in the repository. Authenticate and link the intended
project, inspect the pending changes, and only then apply them:

```sh
npx supabase login
npx supabase link --project-ref <PROJECT_REF>
npx supabase db push --remote --dry-run
npx supabase db push --remote
```

Do not pass credentials as command-line arguments or commit local CLI
state. The linked project reference is stored under the ignored
`supabase/.temp/` directory. When local Docker-based testing is
available, use `npx supabase start` and `npx supabase db reset`; never
link a local or preview environment to production data. The CLI targets
the local database by default; always include `--remote` when applying
migrations to the explicitly linked project.

If a migration fails or needs correction, use a reviewed forward
migration; do not drop the table or delete records as an automatic
rollback.

## 8. Retention, deletion and backups

The product owner set a seven-day retention period for enquiry database
records, starting at submission, and a maximum seven-day target for
stored backups. The product owner confirms that the Supabase backup
setting is configured and verified for this target; this work has not
independently inspected the setting. The application purge is not
implemented or verified and must be completed before collection. This
retention decision alone does not authorize collection.

Before launch, define:

-   Who may access enquiry records.
-   How the seven-day retention period is measured and enforced.
-   How deletion requests are assessed and actioned.
-   Whether backups retain deleted records and whether the seven-day
    maximum is enforced by the configured provider.
-   How database backups and restoration are tested.
-   Whether exports are needed and how they are protected.

## 9. Future platform data

A future farm-management product could require tenant/farm, user,
membership, machinery, maintenance, inventory, detailing and audit
tables. None of those entities should be implemented as part of the
current public website without an approved scope, tenant-isolation
design and data-ownership decision.
